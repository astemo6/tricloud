# TriCloud 代码审查 — 优化空间

**审查对象**：GitHub `astemo6/tricloud` origin/master（`d7d139b`，v1.6.0 build 23）
**审查日期**：2026-10-17
**审查方式**：人工通读核心模块（Pi 三档当时全部不可用，按用户规则直接上手）
**代码规模**：`app/` 约 12,343 行 Python，`web/` 约 3,589 行（HTML/JS/CSS），`tests/` 21 个文件约 6,956 行

**总体评价**：v1.6.0 架构比 10 月初版本成熟很多——`app/main.py` 从 2000+ 行拆到 104 行（路由拆进 `app/routers/`），前端从单文件拆成 ES modules（`web/js/` 15 个模块），安全中间件（鉴权/审计/安全头）设计到位，测试覆盖 21 个文件。hark 演示页提过的功能（健康度、自动抢机、流量守护、密码保险箱、API Token、免费护栏、防爆破）已全部实现。下面是按优先级排序的优化项。

---

## 高优先级

### 1. 备份恢复无回滚机制，中间崩溃会导致数据锁死
- **位置**：`app/security.py` → `restore_backup()`
- **问题**：恢复流程是先 `src.backup(c)` 覆盖 live DB，再写新的 `fernet.key`。如果在 DB 覆盖后、key 写入前进程崩溃（断电、OOM kill），DB 已是新 key 加密、磁盘上仍是旧 key → 所有加密数据永久不可读，面板彻底锁死。
- **影响**：高（数据丢失风险，一次就致命）
- **成本**：小（恢复前先把当前 `tricloud.db` + `fernet.key` 拷到 `.bak`，失败时回滚；成功后删除 `.bak`）

### 2. Dockerfile 信任所有代理 IP，登录锁定可被绕过
- **位置**：`Dockerfile` → `CMD` 中的 `--forwarded-allow-ips "*"` + `--proxy-headers`
- **问题**：uvicorn 信任任意来源的 `X-Forwarded-For`，`request.client.host` 可被伪造。`core.login_failed()` 按 IP 计数锁定——攻击者轮换伪造 IP 即可无限爆破；反过来也可伪造他人 IP 触发误锁。
- **影响**：中（面板暴露公网时真实风险；`client_ip()` 有 `TRUST_PROXY` 开关，但 uvicorn 层面的信任是无条件的）
- **成本**：小（`--forwarded-allow-ips` 改为只信任 Cloudflare IP 段或 `127.0.0.1`，与 `TRUST_PROXY` 语义对齐）

### 3. 500 错误把异常原文返回给客户端
- **位置**：`app/main.py` → `@app.exception_handler(Exception)`
- **问题**：兜底处理器返回 `{type(exc).__name__}: {exc}`，异常原文可能含文件路径、SQL 片段、云 SDK 返回的账号信息。
- **影响**：中（自托管面板，攻击面小，但属信息泄露）
- **成本**：小（500 时只返回 `"服务器内部错误"` + 错误 ID，详情写日志；保留 400/403 的友好提示逻辑）

## 中优先级

### 4. SQLite 单连接 + 全局锁，所有 DB 操作串行化
- **位置**：`app/core.py` → `_conn` 单例 + `db()` 的 `_lock: threading.RLock`
- **问题**：4 个后台 loop（task/monitor/schedule/telegram）+ Web 请求全部争用一把锁。监控实例多时，一个慢的云 API 调用会拖住所有 DB 读写。
- **影响**：中（个人用目前够用；账号/监控上量后延迟明显）
- **成本**：中（开 WAL 模式 + 按线程建连接，或把高频只读走独立连接）

### 5. 监控循环串行检测，一个慢账号拖慢全局
- **位置**：`app/tasks.py` → `monitor_loop()`（第 672 行起）
- **问题**：`for m in monitors:` 循环内逐个 `await asyncio.to_thread(services.get_state, ...)`，是串行的。10 个账号 × 每个 5 秒 = 一轮 50 秒，`monitor_interval` 名存实亡。
- **影响**：中（监控实时性随账号数线性下降）
- **成本**：中（`asyncio.gather` 并发 + `Semaphore(5)` 限流，单个失败不影响其他）

### 6. `params LIKE '%id%'` 脆弱匹配 JSON，易误判
- **位置**：`app/tasks.py:657`、`app/health.py:59`
- **问题**：用 `params LIKE '%{instance_id}%'` 在 JSON 文本里找实例 ID。ID `i-123` 会误匹配 `i-1234`；且 LIKE 前后通配符无法走索引。
- **影响**：中（`tasks.py:657` 用于"已有换 IP 任务在跑则跳过自动换 IP"，误匹配会导致该换的不换；`health.py:59` 用于判断实例是否被删，误匹配会导致"实例消失"漏报）
- **成本**：小（`tasks` 表加 `instance_id` 独立列并建索引；或查询后用 `json.loads` 精确比对）

### 7. 审计每次写入都全表删旧数据
- **位置**：`app/security.py` → `audit()`，每次 INSERT 后 `DELETE FROM audit WHERE ts < ...`
- **问题**：高频操作（批量任务、监控）每次写审计都触发一次全表 DELETE。
- **影响**：低（审计频率不高，但属浪费）
- **成本**：小（移到 `schedule_loop` 每天凌晨清理一次）

### 8. API Token 每次校验都 UPDATE（读变写）
- **位置**：`app/security.py` → `check_api_token()` 内 `UPDATE api_tokens SET last_used`
- **问题**：API Token 每次调用都写 DB。自动化脚本高频调用时会产生大量写。
- **影响**：低
- **成本**：小（抽样更新：如 1% 概率或距离上次更新 >60 秒才写）

## 低优先级 / 代码质量

### 9. `migrate()` 静默吞掉所有迁移异常
- **位置**：`app/core.py` → `migrate()`，`except sqlite3.OperationalError: pass`
- **问题**：本意是忽略"列已存在"，但会同时吞掉真正的迁移错误（如语法错误、类型冲突），升级后表结构不对却无日志。
- **影响**：低（目前没出过事，但隐患）
- **成本**：小（只忽略 `duplicate column name`，其他打日志告警）

### 10. 备份临时文件崩溃残留
- **位置**：`app/security.py` → `make_backup()` 的 `.backup.tmp.db`
- **问题**：`finally` 里删除，但 `kill -9` / 断电会残留，下次备份复用同一文件名（`sqlite3.connect` 会覆盖，倒无大碍，但残留文件占空间）。
- **影响**：低
- **成本**：小（启动时清理 `DATA_DIR` 下 `.tmp.db`；或用 `tempfile` 唯一名）

### 11. requirements 部分依赖无上限 pin
- **位置**：`requirements.txt`
- **问题**：`httpx[socks]>=0.27`、`cryptography>=43`、`boto3>=1.35` 只有下限。`azure-mgmt-resource` 已因大版本拆包 pin 了 `<25`（注释写得很清楚），说明团队吃过亏，但其他包没跟进。
- **影响**：低（构建时拉到不兼容大版本才爆）
- **成本**：小（`pip freeze` 锁定当前可用版本，或至少加 `<` 上限）

### 12. 初始密码打印进 docker logs 长期保留
- **位置**：`app/core.py` → `ensure_password()`，`print(f"[tricloud] 初始面板密码...")`
- **问题**：密码明文进 stdout → docker logs 永久保留。注释说"仅显示一次"，但日志不删就是永久。
- **影响**：低（能看 docker logs 的人本来就有服务器权限）
- **成本**：小（写一次性文件 `.initial-password` 并 `chmod 600`，读取后删除；或仅在无 `PANEL_PASSWORD` 时走此流程——现在已是此逻辑，缺的是"阅后即焚"）
